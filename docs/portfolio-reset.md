# P-U-C Portfolio Reset

## Why this exists

P-U-C has accumulated useful products, infrastructure, experiments, and historical work faster than it has made choices about what belongs in the current portfolio. This reset is the public record of making those choices.

The goal is a smaller, clearer organization: people should be able to see what P-U-C makes now, why each active project exists, where it is operated, and what work is genuinely next.

This page tracks the reset. It does not publish private operating details, credentials, or a claim that every historical repository is active.

## Ground rules

- Evidence before narrative: public status is checked before it is described.
- No deletion, archival, transfer, visibility change, or default-branch change without an explicit decision.
- A repository is not active because it has ideas, old issues, or a nice name. It needs an owner and a current proof.
- Historical work stays findable, but does not crowd out the projects that are operating now.
- Changes ship in focused pull requests, with tests and visual verification where relevant.

## The work

### 0. Restore the front door

- [ ] Diagnose and resolve the primary-site availability incident.
- [ ] Establish the canonical organization entry point and ownership for it.
- [ ] Replace stale top-level copy with a portfolio map that can be kept current.

### 1. Build the portfolio registry

- [ ] Give every repository one lifecycle label: **Core**, **Product**, **Incubating**, **Paused**, **Archived**, or **Fork retention**.
- [ ] For every Core/Product repository, record its audience, owner, canonical URL, current state, dependencies, and next proof.
- [ ] Record the reason any retained fork remains in the organization.
- [ ] Publish an archive index so completed or retired work remains discoverable without being presented as current.

### 2. Make active work legible

- [ ] Add accurate descriptions, topics, homepages, and concise README contracts to selected active repositories.
- [ ] Declare default-branch exceptions rather than allowing branch names to drift without explanation.
- [ ] Repair or explicitly retire failing automation and stale issue queues.
- [ ] Link public products to their canonical documentation and current operating status.

### 3. Choose, then finish

- [ ] Limit the active major bets to a small, named set.
- [ ] Give each one a smallest end-to-end milestone, an owner, a date, and a stop condition.
- [ ] Do not add a new product to the public portfolio until it has a clear user, working proof, and maintenance path.

## Definition of done

The reset is complete when a new contributor can understand P-U-C in under five minutes; every unarchived repository has an intentional lifecycle state; the public profile only claims current work; the primary entry point is healthy; and the active portfolio has a small, ordered backlog rather than a collection of disconnected ideas.

## Tracking

This charter and its related pull requests record the concrete decisions as they land. Repository issues are disabled here, so the portfolio decision log will live in reviewed documentation until a public project board is deliberately enabled. Detailed operational inventory and private system evidence remain private by design.
